# M5: فهم Socket.IO في FoodFlow

M5 هي مرحلة المطبخ والتحديثات المباشرة. هذا التنفيذ يخص Backend فقط؛ واجهة
المطبخ وتتبع الطلب داخل المتصفح ستُنفّذ لاحقًا. الاختبارات الحالية تستخدم
اتصالات Socket.IO حقيقية من Node.js مع قاعدة PostgreSQL محلية معزولة.

## 1. دور HTTP ودور Socket.IO

HTTP ينفّذ العمليات: إنشاء الطلب، تغيير حالته، وجلب البيانات. Socket.IO
ينقل التحديث إلى الاتصالات المعنية فور حدوثه. كلاهما يعمل على نفس HTTP
Server ونفس المنفذ.

```text
موظف المطبخ يرسل PATCH عبر HTTP
→ التحقق من هويته وعضويته في الفرع
→ التحقق من الانتقال ورقم revision
→ حفظ التغيير في PostgreSQL
→ إرسال order.ready عبر Socket.IO
→ العميل والمطبخ يستقبلان الإشعار
→ جلب التفاصيل الحالية من API
```

Socket.IO مكتبة لها بروتوكولها؛ ليست اتصال WebSocket خامًا. يمكن أن تستخدم
HTTP long-polling ثم تنتقل إلى WebSocket عندما يتاح ذلك. لا يلزم تغيير منطق
الأحداث عندما تتغير وسيلة النقل.

اقرأ `src/http-server.ts` أولًا: يجمع Express وSocket.IO. ثم `src/server.ts`:
يشغّل السيرفر ويغلق الاتصالات قبل فصل قاعدة البيانات عند إيقاف التطبيق.

## 2. Handshake والتحقق من الهوية

مسار الاتصال هو `/api/socket.io`. Cookie الدخول الحالية تستخدم `Path=/api`،
ولذلك يرسلها المتصفح لهذا المسار. المسار الافتراضي `/socket.io` لا يقع تحت
هذا النطاق.

في `src/modules/realtime/realtime.server.ts`، تعمل `io.use` قبل قبول اتصال
Socket.IO. تستدعي `RealtimeService.authenticate` التي:

1. تستخرج JWT من Cookie `foodflow_access`.
2. تتحقق من التوقيع والصلاحية والمُصدر والجهة المستقبلة.
3. تتحقق من وجود المستخدم ومن توافق دوره الحالي مع JWT.
4. تحفظ الهوية المتحقق منها في `socket.data.auth`.

لا نقبل `userId` أو JWT داخل `handshake.auth`. عند الرفض، يستقبل المتصل
`connect_error`. يسمح السيرفر فقط بـOrigin المطابق لـ`FRONTEND_URL`، سواء
استُخدم polling أو WebSocket.

Middleware الاتصال تعمل مرة واحدة لكل اتصال. لهذا نعيد التحقق عند الاشتراك
وقبل إرسال تحديثات، ونضع مؤقتًا يغلق الاتصال عند انتهاء JWT. تسجيل الخروج
يغلق كل اتصالات المستخدم الحالية. نظام JWT الحالي لا يتضمن إبطالًا دائمًا
للتوكن أو refresh token؛ إعادة الاتصال بعد انتهاء الصلاحية تحتاج تسجيل دخول
جديدًا. إزالة Cookie من المتصفح وحدها لا تُغلق اتصالًا مفتوحًا، ولذلك أضفنا
فصل الاتصالات أثناء logout.

## 3. Rooms وتوجيه الأحداث

Room مجموعة اتصالات على السيرفر. يمكن أن تمثل حسابًا له عدة نوافذ، أو مطبخ
فرع له عدة موظفين. ليست جدولًا في قاعدة البيانات ولا وسيلة لمنح الصلاحيات.

كل اتصال ينضم تلقائيًا إلى:

```text
user:{authenticatedUserId}
```

الهوية تأتي من Cookie، وليس من اسم غرفة يرسله العميل. المطبخ يطلب الاشتراك
في فرع واحد بإرسال الحدث:

```text
kitchen.subscribe
payload: { restaurantId }
```

السيرفر يقبل الاشتراك فقط إذا كانت عضوية المستخدم `OWNER` أو `MANAGER` أو
`KITCHEN` في الفرع نفسه، ثم يضيفه إلى:

```text
restaurant:{restaurantId}:kitchen
```

الرد على الاشتراك هو acknowledgement:

```json
{ "success": true, "restaurantId": "branch-id" }
```

عند الرفض:

```json
{
  "success": false,
  "error": { "code": "FORBIDDEN", "message": "Kitchen access denied" }
}
```

Ack هنا يؤكد معالجة طلب الاشتراك؛ لا يؤكد استلام كل تحديث مستقبلي. يتوفر
`kitchen.unsubscribe` بنفس payload للخروج من الغرفة. عمليات الاشتراك والخروج
متسلسلة لكل اتصال حتى لا يتجاوز اشتراك بطيء طلب خروج أحدث.

قبل نشر حدث، نختار اتصال صاحب الطلب واتصالات غرفة الفرع فقط، ونعيد التحقق
من الهوية والعضوية. العضوية المسحوبة لا تستمر في استلام بيانات المطبخ.
الاتصال الموجود في الغرفتين يستقبل الحدث مرة واحدة.

## 4. مسارات المطبخ وحالات الطلب

```text
GET /api/restaurants/:restaurantId/kitchen/orders
PATCH /api/restaurants/:restaurantId/kitchen/orders/:publicId/status
```

قائمة المطبخ تعرض الحالات النشطة فقط: `PENDING`, `CONFIRMED`, `PREPARING`,
`READY`. تدعم `page`, `limit`, وفلتر `status` نشط، وتُرتب حسب `prepDueAt` ثم
وقت الإنشاء والمعرّف. كلا المسارين يتحقق من عضوية الحساب في الفرع.
الدور العالمي `ADMIN` وحده لا يمنح صلاحية المطبخ.

مثال طلب تغيير الحالة:

```json
{ "status": "PREPARING", "revision": 1 }
```

التسلسل المسموح:

```text
PENDING → CONFIRMED → PREPARING → READY → COMPLETED
```

لا يُسمح بتجاوز مرحلة أو الرجوع إلى الخلف. إلغاء العميل يظل مسموحًا أثناء
`PENDING` فقط. المطبخ لا يرسل حالة `CANCELLED` عبر مسار التحضير.

رقم `revision` يبدأ من صفر ويزداد مع كل تغيير حالة. Repository يحدث الصف
فقط إذا كان الفرع والحالة الحالية وrevision مطابقين للنسخة التي راجعها
Service. إذا حاول موظفان تعديل النسخة نفسها، ينجح أحدهما ويحصل الآخر على
`409`. عليه جلب الحالة الحالية قبل المحاولة مجددًا.

اقرأ `kitchen.service.ts` لقواعد الانتقال، و`order.repository.ts` للتحديث
المشروط الذي يحمي من التزامن. إرسال `order.ready` من المتصل لا يُغير قاعدة
البيانات؛ أحداث حالة الطلب تُرسل من السيرفر فقط.

## 5. وقت التحضير والبيانات التاريخية

أضفنا `prepTimeMinutesSnapshot` لكل صنف عند الشراء. الموعد `prepDueAt` يساوي
وقت إنشاء الطلب زائد أطول وقت تحضير بين أصنافه، بافتراض التحضير المتوازي.
هذا تقدير لترتيب الأولوية، وليس وعدًا بوقت التسليم أو محاكاة لسعة المطبخ.

Migration تعطي الطلبات القديمة موعدًا بعد 15 دقيقة من الإنشاء، ووقت تحضير
افتراضيًا 15 دقيقة لأصنافها، لأن وقت التحضير التاريخي لم يكن محفوظًا.

## 6. الأحداث بعد الحفظ

الأحداث الستة:

```text
order.created
order.confirmed
order.preparing
order.ready
order.completed
order.cancelled
```

كل حدث يحمل نفس الشكل:

```json
{
  "publicId": "order-public-id",
  "restaurantId": "branch-id",
  "status": "READY",
  "revision": 3,
  "updatedAt": "2026-10-02T09:00:00.000Z"
}
```

لا تُرسل أسعار أو عناوين أو توكنات في الحدث. الهدف إبلاغ المستمع بأن طلبًا
تغير؛ API يعيد التفاصيل بعد التحقق من صلاحياته.

`OrderService` و`KitchenService` يعتمدان على واجهة `OrderEvents`. لا يستدعي
Controller Socket.IO مباشرة. `notifyOrder` تعمل بعد عودة transaction الناجحة.
فشل الحفظ لا يرسل حدثًا. إعادة Checkout بالمفتاح نفسه وإعادة إلغاء طلب
مُلغى لا ترسل أحداثًا مكررة.

إذا فشل الإشعار بعد نجاح الحفظ، لا نعيد فشل عملية الشراء ولا نتراجع عن طلب
محفوظ؛ نكتب رسالة تشخيص قصيرة وتظل الحالة متاحة عبر API. لا يوجد outbox
دائم في M5، ولذلك قد تضيع رسالة إذا توقف السيرفر بين الحفظ والنشر.

## 7. انقطاع الاتصال وإعادة المزامنة

Socket.IO لا يحتفظ افتراضيًا بكل أحداث السيرفر التي فاتت اتصالًا منقطعًا.
PostgreSQL هي المصدر المعتمد للحالة.

عند ربط الواجهة لاحقًا:

1. سجل مستمعي الأحداث قبل إجراء تغييرات.
2. عند `connect`، ينتسب العميل تلقائيًا لغرفته الخاصة.
3. المطبخ يعيد إرسال `kitchen.subscribe` وينتظر Ack ناجحًا.
4. اجلب تفاصيل الطلب أو قائمة المطبخ من HTTP بعد الاشتراك.
5. عند وصول حدث، أعد جلب الحالة من API.
6. استخدم `revision` لتجنب استبدال نسخة حديثة بأخرى أقدم.

لم نُفعّل استعادة غرف قديمة دون التحقق من الصلاحيات. الاتصال الجديد يُصادق
عليه من جديد. انتهاء JWT يسبب فصلًا من السيرفر؛ يحتاج المستخدم تجديد الدخول
ثم فتح اتصال جديد. الإعداد الحالي يستخدم سيرفرًا واحدًا وغرفًا في الذاكرة؛
تشغيل عدة نسخ يحتاج adapter مشتركًا وإعداد نشر إضافيًا.

## 8. كيف تتعلم من الاختبارات

افتح `tests/realtime.integration.test.ts`. الاختبارات تنشئ اتصال عميل واتصال
مطبخ حقيقيين باستخدام `socket.io-client` داخل Backend فقط. لا تغيّر ملفات
`client/` ولا تستخدم قاعدة المشروع.

تبدأ باختبار رفض الاتصال غير الموثق، ثم الاشتراك، ثم إنشاء الطلب واستقبال
`order.created`، ثم كل انتقال واستقبال الحدث المقابل. توجد اختبارات لعزل
العملاء والفروع، وتزامن الموظفين، وفشل الحفظ والنشر، وسحب العضوية، والخروج
من الغرفة، وإعادة الاتصال، وانتهاء JWT.

```sh
npm run prisma:generate
npm run typecheck
npm run lint
npm run build
TEST_DATABASE_URL=postgresql://USER@127.0.0.1:PORT/foodflow_m4_test npm test
```

قاعدة الاختبار المحلية يجب أن تُسمى `foodflow_m4_test` لأسباب توافق الاختبارات
الحالية. الاختبارات تمسح public schema فيها، ثم تطبق كل migrations. لا تستخدم
هذه القاعدة لبيانات تحتاج الاحتفاظ بها. بدون `TEST_DATABASE_URL` تُتخطى
اختبارات التكامل.

لتشغيل التطبيق على قاعدة التطوير، راجع `DIRECT_URL` ثم طبّق migrations
باستخدام `npx prisma migrate deploy` من `server/`.
